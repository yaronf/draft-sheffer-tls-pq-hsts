              An HSTS-like Header for Secure PQ Migration
                    draft-sheffer-tls-pq-hsts-latest

Abstract

   This document defines an HTTP response header field, Require-PQ-Auth,
   that instructs user agents to require a quantum-resistant certificate
   chain in subsequent connections.  This is a short-term, opt-in
   mechanism for HTTP origins to protect against legacy classical trust
   anchors.  It will become unnecessary when UAs remove these trust
   anchors.

1.  Introduction

   Migrating TLS authentication to post-quantum cryptography cannot be
   done by flipping a single switch.  For a long period, many origins
   will still present classical certificate chains, so user agents (UAs)
   will need to trust classical trust anchors alongside quantum-
   resistant ones.  This allows an attacker able to forge classical
   certificates to downgrade the connection.  Whether or not the origin
   had actually upgraded, a client that still accepts classical paths
   will treat that forged credential as valid.

   This document defines an HTTP response header field, Require-PQ-Auth,
   which allows an origin to indicate to the user agent to only accept
   chains from quantum-resistant trust anchors in subsequent
   connections.

   This is a near-term mechanism with several limitations described in
   Section 7.3.  It is intended to be temporary, for use until classical
   trust anchors are removed.  [ChromiumPQAuthRoadmap] describes an
   example roadmap to do so.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   The following terms are used in this document:

   classical:  Cryptography or credentials that are not designed to
      remain secure against a cryptographically-relevant quantum
      computer (CQRC), such as RSA or elliptic-curve public-key
      algorithms.  A classical trust anchor is a trust anchor that
      authenticates only classical paths.

   quantum-resistant (signatures / trust anchors):  Not classical-only.
      For authentication material, this document treats pure post-
      quantum algorithms and composite algorithms
      [I-D.ietf-lamps-pq-composite-sigs] as one class, consistent with
      the PQC end-entity classification in
      [I-D.sheffer-tls-pqc-continuity].  Which algorithms a UA accepts
      as quantum-resistant is a matter of local policy and the relevant
      algorithm specifications; this document states the property, not a
      closed algorithm list.


   // TODO: add a more precise definition of quantum-resistance for MTC.

   quantum-resistant (key agreement):  Not classical-only.  Hybrid key
      agreement (classical combined with a post-quantum KEM) and pure
      post-quantum key agreement both satisfy this document.  Exact
      NamedGroup / codepoint acceptance is left to UA policy and the TLS
      Supported Groups registry [IANA.TLS-Parameters].

   trust anchor:  The root of acceptance for a server credential: an
      X.509 trust anchor [RFC5280] or an MTC trust base / cosigner trust
      as defined by [I-D.ietf-plants-merkle-tree-certs].  Normative
      requirements in this document refer to the class of trust anchor
      (classical vs quantum-resistant), not to a single encoding.

   HSTS terms:  This document refers to Known HSTS Host, HSTS Policy,
      and related terminology from [RFC6797] only for comparison.  HSTS
      state is independent of the policy defined here.

   Known PQ Host / PQ Policy:  A host for which the UA has noted a valid
      Require-PQ-Auth policy (Section 3, Section 5), including expiry
      derived from max-age and whether include-subdomains applies.
      Storage is parallel to—not part of—HSTS Policy storage.

   superdomain:  As in [RFC6797], a domain name of which another domain
      name is a subdomain.  For example, example.com is a superdomain of
      www.example.com.

3.  Syntax

   Require-PQ-Auth is an HTTP Structured Header field [RFC9651].  Its
   value MUST be a Dictionary.  Recipients that cannot parse the field
   value as a Dictionary MUST NOT update any Noted PQ Policy for the
   host based on that field (any previously Noted policy remains
   unchanged).

   The following Dictionary members are defined.  Keys are lowercase as
   required by Structured Fields.  Unknown members MUST be ignored.
   Recognized members are processed as specified below when the
   Dictionary parses successfully.

   max-age:  Integer (required).  Non-negative number of seconds after
      receipt during which the UA regards the host as a Known PQ Host
      with this policy.  A value of 0 signals the UA to delete any Noted
      PQ Policy for the host (including subdomain scope learned from
      this host).

   include-subdomains:  Boolean true if present as a bare Dictionary
      member (optional).  If present, the PQ Policy applies to the host
      and to hosts whose domain names are subdomains of that host's
      domain name, analogous to HSTS includeSubDomains [RFC6797] but
      applying only to this PQ Policy.  Absence means host-only scope.

   If the Dictionary does not include a usable max-age, or if any
   present member is malformed for its type, the UA MUST NOT update
   Noted PQ Policy from this field.

   Examples:

   Require-PQ-Auth: max-age=86400
   Require-PQ-Auth: max-age=31536000, include-subdomains

4.  Server Processing

   Servers MUST emit Require-PQ-Auth only when they can keep the
   following commitment for the lifetime conveyed by max-age (and for
   any hosts covered by include-subdomains):

   1.  Serve a certification path anchored at a quantum-resistant trust
       anchor (pure post-quantum or composite per the server's
       deployment), with no mixed classical/quantum-resistant path; and

   2.  Complete quantum-resistant key agreement (hybrid or pure post-
       quantum) with clients that implement this document.

   The commitment applies to every server that answers for each covered
   hostname, not only the instance that sent the header—including all
   CDN edges, failover or backup providers, and HTTP/3 endpoints
   advertised via Alt-Svc [RFC7838].  If any such endpoint cannot meet
   the policy, UAs that reach it will fail to connect.

   The server MUST send Require-PQ-Auth only over HTTPS.  Otherwise UAs
   will not note the field (Section 5).  The server SHOULD include the
   header on every HTTPS response, unless it omits the header for
   performance reasons (which typically does not make sense given the
   header's small size).

4.1.  Choosing policy parameters

   max-age should reflect how long the operator is willing to keep the
   commitment above.  Operators typically start with a short max-age
   while gaining confidence, then increase it.

   include-subdomains MUST NOT be sent unless every host that would be
   covered can likewise satisfy the commitment for the same window.

4.2.  Updating and clearing policy

   A valid Require-PQ-Auth field replaces any previously Noted PQ Policy
   for that host when the UA notes it (Section 5).  Omitting the header
   does not clear Noted policy.

   To delete client state before expiry, the server sends max-age with
   value 0.  UAs that successfully note that response MUST delete the
   Noted PQ Policy (Section 5).  That escape hatch is useful only in
   laboratory or similar conditions, where the client population is
   small and individually identifiable.  It works only while the server
   can still meet the commitment: enforcing UAs reject connections that
   do not, and so never see the clear.  Operators should keep meeting
   the commitment until outstanding pins expire.  If the server loses
   that ability first, those UAs stay locked out until expiry or manual
   action.

5.  User Agent Behavior

   This section defines how UAs note and enforce Require-PQ-Auth policy.

5.1.  Noting the header

   Upon receipt of a Require-PQ-Auth header field in an HTTP response,
   the UA notes a PQ Policy when all of the following hold, and MUST NOT
   note one otherwise:

   1.  The response was received over an error-free HTTPS connection
       that uses TLS 1.3 [RFC9846] or later.

   2.  That connection meets the checks in Section 5.2, whether or not a
       PQ Policy is already Noted for the host.

   3.  The field value parses as a Structured Fields Dictionary per
       Section 3, including a valid max-age member.

   The host need not be a Known HSTS Host.  Noting PQ Policy MUST NOT
   modify HSTS Policy storage.

   When noting, the UA MUST:

   1.  Store a PQ Policy for the host as a Known PQ Host, with expiry
       derived from max-age (or delete the policy if max-age is 0).

   2.  Record subdomain scope from include-subdomains when that member
       is usable; otherwise host-only scope.

   If a subsequent valid Require-PQ-Auth field is noted for the host, it
   replaces the prior PQ Policy (including subdomain scope) for that
   host.  Absence of the header field on a later response does not by
   itself clear PQ Policy before expiry; servers clear state with max-
   age of 0.

   UAs MAY additionally configure other hosts as Known PQ Hosts via
   local policy.  For example, the UA MAY be pre-configured with a list
   of pre-loaded Known PQ Hosts, similar to Section 12.3 of [RFC6797].

5.2.  Connection checks

   A connection meets the checks of this section when all of the
   following hold.  These checks apply to the connection itself.  They
   do not depend on a PQ Policy already being Noted.

   1.  The trust anchor that caused acceptance is quantum-resistant
       (pure post-quantum or composite per local policy), whether that
       trust anchor is an X.509 trust anchor or an MTC trust base /
       cosigner.

   2.  The accepted certification path is entirely quantum-resistant: no
       hop is classical.  (Detailed mixed-path rejection may be refined
       here or by reference to a dedicated path-validation document.)

   3.  The negotiated key agreement is quantum-resistant (hybrid or pure
       post-quantum per local policy).

5.3.  Enforcement

   When establishing a connection to a host covered by an unexpired
   Noted PQ Policy — either because the host itself is a Known PQ Host,
   or because a Known PQ Host that is a superdomain of this host has
   include-subdomains — the connection MUST meet the checks in
   Section 5.2, and MUST use TLS 1.3 [RFC9846] or later.

   If the connection does not meet those requirements, the UA MUST abort
   the TLS handshake with a fatal "handshake_failure" alert ([RFC9846],
   Section 6.2).  The UA MUST NOT offer the user a way to proceed
   (Section 12.1 of [RFC6797]).

   This document does not impose separate end-entity signature-algorithm
   requirements beyond the trust-anchor class and path-consistency rules
   above.  It does not enumerate TLS NamedGroup codepoints or MTC
   validation procedures; those remain matters for TLS/IANA policy and
   [I-D.ietf-plants-merkle-tree-certs], respectively.

   Once classical trust anchors are no longer accepted for
   authentication, Require-PQ-Auth is redundant.  UAs MAY clear PQ
   Policy for Known PQ Hosts when local policy determines that the pin
   is obsolete.  Servers SHOULD stop sending the header in that
   environment.  HSTS policy, if any, is unaffected.

7.  Security Considerations

   The security considerations of HSTS (Section 14 of [RFC6797]) apply
   to Require-PQ-Auth.  This section covers where they differ.

7.1.  Underlying Secure Transport Considerations

   Quantum-resistant key exchange and authentication are specified for
   TLS 1.3 [RFC9846] and not for earlier versions.  Require-PQ-Auth can
   therefore be used only with TLS 1.3 or later.

7.2.  Non-Conformant User Agent Implications

   UAs that do not implement this document ignore the header field.  If
   such a UA accepts both classical and quantum-resistant
   authentication, a quantum attacker can present a forged classical
   certificate even when the server offers a quantum-resistant one.

7.3.  Limitations

   As with HSTS, noting a PQ Policy does not protect initial visits to
   an origin.  An attacker who can modify that first response can strip
   Require-PQ-Auth, and the UA never notes the policy.  Additionally,
   UAs might limit state set by an origin, e.g. as part of private
   browsing modes or to protect against cross-sign tracking
   [ProtectingAgainstHSTSAbuse] [StrictNavigationalSecurity].  When
   state is limited, there are more "initial" responses for an attacker
   to intercept.

   Section 5.1 permits UAs to configure other Known PQ Hosts as local
   policy, such as a pre-configured list.  Which such measures can
   mitigate this attack, they can introduce other limitations when the
   number of otherwise quantum-resistant hosts exceeds an
   implementation's size limits.

   Non-browser clients may be further limited in their ability to both
   maintain state and include large, pre-configured lists.

   These limitations mean Require-PQ-Auth is only viable as a temporary
   measure for a limited number of applications.  In many applications,
   it will still be necessary to trust anchors in the near term.
   [ChromiumPQAuthRoadmap] describes one such transition plan.

7.4.  Denial of Service

   An attacker that controls a TLS-terminating proxy can cause a UA to
   note Require-PQ-Auth only when the connection meets Section 5.2.  A
   proxy that cannot meet those checks cannot set the policy.

   If the attacker can meet the checks and sets a large max-age, UAs
   that note the policy require Section 5.2 until the policy expires.
   include-subdomains extends that requirement to every covered name.
   Sending max-age of 0 does not remove the policy unless some endpoint
   the UA will accept can still meet Section 5.2 and deliver that value
   (Section 4).  If the attacker was the only such endpoint and then
   stops meeting the checks, the origin stays unreachable until the
   policy expires.

   After a policy is legitimately Noted, a TLS interceptor that cannot
   meet Section 5.2 causes the same hard failure.  That is an
   availability problem for deployments that intercept TLS, separate
   from injection.
